# [Dead Hub](https://dead-hub.vercel.app/)

Фан-сайт сообщества для игры **Deadlock** (Valve) — справочник по героям, каталог и таблица предметов со статистикой, матчапы (контрпики и синергии), помощник драфта (какого героя взять против вражеской команды), профили игроков с историей матчей и страницей каждого матча (таблица игроков, покупки, перевес по душам, хроника убийств), «мой профиль», распределение по рангам, лидерборд, интерактивная карта города, страница последнего обновления, тир-лист по данным и конструктор, сравнение и генератор случайного билда. Статистика — за период, ранги и режим (обычные матчи или Street Brawl), с изменением к прошлому периоду и недельной динамикой. Данные загружаются с [deadlock-api.com](https://deadlock-api.com).

## Фильтры статистики

Период, диапазон рангов (от Initiate до Eternus) и режим игры — общие для всего сайта: панель `StatsFilters` есть на странице героев, мете, матчапах, страницах героя и предмета и на карте (когда включена тепловая карта); на главной панели нет — там только подпись «Данные: С патча · Ранг: Все» со ссылкой на мету. Выбор хранится в `localStorage` (`dlhub_filters`).

Период — это **«С патча»** либо 7 / 14 / 30 / 90 дней. Пока последнее обновление моложе 21 дня, по умолчанию выбрано «С патча»: окно «30 дней» наполовину состоит из данных до обновления (другие герои, предметы и карта). Время обновления берётся из ленты `/v2/patches` (новости Steam) и хранится прямо в фильтрах (`since`), поэтому адрес запроса и ключ кеша определяются самим объектом фильтров.

Ранг выбирается готовым диапазоном (Все / Низкие 1–4 / Средние 5–8 / Высокие 9–10 / Этернус) либо двумя списками. На экране уже 720 px панель свёрнута в строку-сводку («С патча · Ранг: Все»), чтобы список героев не уходил за первый экран; нажатие раскрывает её.

Статистика героев берётся из `GET /v1/analytics/hero-stats` — **одним запросом на всех героев**. Винрейт — доля побед героя, пикрейт — доля героя среди всех пиков выборки (сумма по героям 100%). Под панелью показан размер выборки: при узких фильтрах (высокие ранги, короткий период) цифры «шумят», и сайт об этом предупреждает.

Начало периода округляется до суток (UTC), чтобы адрес запроса не менялся каждую секунду — иначе не работал бы ни кеш браузера, ни CDN.

**Режим** — «Обычный» либо **Street Brawl** (`game_mode=street_brawl`). У Street Brawl нет рангов: API отвечает `400 Cannot filter by average badge for street brawl game mode`, поэтому в этом режиме выбор ранга скрыт, диапазон не уходит в запрос и не входит в ключ кеша (при возврате к обычным матчам прежний диапазон снова действует). Тепловая карта убийств всегда строится по обычным матчам — у Street Brawl другая арена; на карте переключатель режима скрыт. Режим работает на всех страницах со статистикой: он добавляется к тем же запросам (`hero-stats`, `item-stats`, матчапы, сборки).

## Изменение к прошлому периоду (Δ)

Колонка «Δ WR» на странице героев, подписи на карточках и странице героя, блок «Победители и проигравшие» на мете и на странице обновления. Это **один дополнительный запрос** `hero-stats` с `max_unix_timestamp` (текущая статистика уже есть в кеше — по ней строится список героев): «с патча» сравнивается с периодом между предыдущим обновлением и текущим, «N дней» — с предыдущими N днями (`previousWindow` в `services/deltaService.js`). Прошлый период кешируется на 6 часов.

Разница винрейта без оговорок вводит в заблуждение: на сотнях матчей он «скачет» от случайности. Поэтому у каждой Δ два признака: **достаточно матчей** (≥ 300 в обоих периодах, иначе показан прочерк) и **значимость** — разница двух долей выходит за 95% доверительный интервал (|z| ≥ 1,96). Стрелки ▲▼ и цвет — только у значимых изменений; в «победителей и проигравших» попадают только они.

## Динамика героя по неделям

Блок «Динамика» на странице героя: винрейт и пикрейт по неделям за последние 10 недель. **Один запрос на всех героев** (`hero-stats?bucket=start_time_week`, ~250 КБ → в кеше несколько КБ, `slimWeeklyStats`), и уходит он, только когда блок подошёл к экрану (`useInView`). Неделя с менее чем 200 матчей героя пропускается, первая и текущая недели (неполные) нарисованы пустой точкой. Своей базы с историей по дням у сайта нет: недельные корзины даёт сам API, а повторные запросы разных посетителей гасит кеш на краю Vercel.

## Предметы

Страница `/items` показывает предметы тремя видами; выбор запоминается в `localStorage` (`dlhub_items_view_v2`). Общие для всех видов фильтры: поиск, слот (на кнопке — число предметов), тип (активный / пассивный), флажки «Есть Corrupted» и «Отключённые», вкладки тиров.

- **Магазин** (по умолчанию). Тиры по цене — 800 / 1600 / 3200 / 6400 и «легендарные» за 9999 — и в каждом три колонки: оружие, живучесть, дух. Тиры I–II раскрыты, остальные свёрнуты в строку-заголовок; в колонке длиннее девяти предметов видны первые четыре и кнопка «Ещё N» (`shopService.visibleRows`). Вкладки тиров прокручивают к разделу, подсвечен тот, что на экране (`useScrollSpy`). Сортировка: по алфавиту, по покупаемости, по винрейту (предметы с малой выборкой — в конец). Щелчок по предмету открывает **панель**: справа, приклеенную к странице (от 1000 px), а на узком экране — выезжающую снизу (закрывается крестиком и Esc). В ней: слот · тир · тип и цена, характеристики из подсказки предмета, винрейт и доля покупок по общим фильтрам статистики (с подписью «С патча · Ранг: Все» и ссылкой на таблицу, где фильтры меняются), из чего предмет собирается и во что улучшается (по `component_items` каталога; щелчок переходит к соседнему предмету), герои, которые берут его чаще всех, и ссылка на страницу предмета.
- **Сетка**: карточки по тирам с подсказкой-характеристиками, щелчок открывает страницу предмета.
- **Таблица статистики**: данные — `item-stats` **одним запросом на все предметы** (тот же запрос и кеш, что у страниц предметов); при выборе героя — запрос, общий со страницей героя. Частота покупки — доля матчей, где предмет купили (для героя — от его матчей). У предметов меньше 100 покупок цифры шумят: строка блёклая, а сортировка по числу всегда оставляет такие строки внизу. Вкладки тиров здесь работают как фильтр. Код таблицы грузится отдельным файлом.

**Поиск** смотрит в название, описание и подписи характеристик («лечение», «замедление»): все слова запроса должны найтись, слова короче трёх букв ищутся только в названии, «ё» и «е» не различаются. Клавиша `/` на этой странице ведёт именно в этот поиск; общий поиск сайта остаётся на кнопке в шапке и Ctrl/⌘+K.

**Данные и запросы.** Каталог предметов общий для всего сайта (6 часов); при загрузке он облегчается: добавлены `class_name`, `component_items` и `is_active_item`, а из описаний убраны встроенные значки-SVG (около 100 КБ на список) — ключ кеша `items_upgrades_v2_*`, прежний удаляется сам. Магазин на широком экране сразу показывает панель, поэтому берёт статистику одним запросом на все предметы (`item-stats`) и разбивку по героям (`item-stats?bucket=hero`, около 1,4 МБ до сжатия) — оба запроса те же, что у страницы предмета и таблицы, и общий кеш на 10 минут. На телефоне оба запроса уходят после первого щелчка по предмету, в сетке — только если выбрана сортировка по цифрам. **Чего страница не показывает:** «новое в патче» и «изменено в патче». В API у предметов нет такого признака (`update_time` заполнен у трети предметов, и последняя дата — май 2026, до обновления City Never Sleeps), а вычитывать названия из текста заметок — гадание; выдумывать числа сайт не станет.

## Случайный билд

`/build` открывается **билдом дня**: зерно считается от местной даты посетителя (`YYYY-MM-DD`), поэтому в один день у всех один билд, а адрес без параметров всегда ведёт на него. Настройки: герой (или «любой»), слоты (оружие / дух / живучесть), распределение («Баланс» — поровну из каждого выбранного слота, «Полный рандом»), бюджет душ (10 000–80 000; это верхняя граница — самый дорогой предмет заменяется более дешёвым того же слота) и «без бесполезных для героя предметов» (предмет, который на этом герое покупают реже чем в 1% матчей; один запрос `item-stats` на героя, общий со страницей героя, и только пока галочка стоит). Билд — 12 предметов в трёх этапах покупки по цене (4 / 4 / 4) с итогом по слотам. Замок закрепляет предмет: при «Перебросить» остаются герой и закреплённые предметы, остальное меняется; клавиша `R` — новый бросок. Последние броски лежат в `localStorage` (`dlhub_build_history`), по щелчку бросок возвращается на экран.

**Детерминизм.** Случайных чисел и перемешивания нет: у каждого героя и предмета есть «приоритет» — хеш от зерна и идентификатора, берётся подходящий с наименьшим. Поэтому один адрес даёт один билд, а новые предметы в каталоге почти не переставляют прежние броски. Зерно показано как `#A7F3-29`; адрес `?seed=&hero=&slots=&mode=&budget=&useful=0&pin=` воспроизводит бросок целиком (значения по умолчанию не пишутся, «Поделиться» всегда кладёт зерно). Логика — чистый `services/buildService.js` с тестами.



## Тир-лист по данным

Формула открыта и показана на странице вместе с оценкой каждого героя (`services/tierService.js`):

- оценка = **0,8 × процентиль винрейта + 0,2 × процентиль пикрейта** среди героев с достаточной выборкой (≥ 0,4% всех пиков);
- **S** — лучшие 10% по оценке, **A** — следующие 20%, **B** — 40%, **C** — 20%, **D** — последние 10%;
- тиры относительны, поэтому рядом показан разброс винрейта между первым и последним героем; период, ранги и режим берутся из общих фильтров.

В «Конструкторе» кнопка «Заполнить по данным» расставляет героев по этому тир-листу — дальше его можно править руками.

## Помощник драфта

`/draft`: отметь героев вражеской команды (до 6), союзников (до 5) и недоступных — список «Лучшие пики» пересчитывается (`services/draftService.js`). Выбор лежит в адресе (`?e=1,2&a=3&x=4&r=Role`), драфтом можно делиться ссылкой. Новых запросов к API нет: матрицы матчапов и список героев — те же запрос и кеш, что у `/matchups`.

**Как считается.** «Винрейт героя против X» почти целиком говорит о силе X, а не о паре: на реальных данных (30 дней, все ранги) около 95% разброса — это просто сильный противник, а настоящий контр-эффект пары — порядка ±0,7 п.п. Поэтому для каждой пары берётся «чистый» эффект: WR пары − обычный WR героя ± сила второго героя (для контрпика плюс, для синергии минус). Эффекты малы и шумны, и каждый сглаживается к нулю (эмпирический Байес): дисперсия настоящих эффектов τ² оценивается по самой матрице, поэтому чем короче период и уже ранги, тем сильнее сглаживание. Скорректированный WR = обычный WR героя + сумма сглаженных эффектов против выбранных врагов и вместе с союзниками. У каждой строки есть разбор по парам и «уверенность» (насколько мало сгладили). Если на выбранной выборке эффекты неотличимы от шума, страница так и пишет, а порядок идёт по силе героя.

**Чего помощник не делает.** Модель складывает вклады героев: она не знает про линии, сборки и умение игроков — это подсказка, а не прогноз матча. «Предметы против врагов» не предлагаются сознательно: выборка по паре «предмет — вражеский герой» слишком мала, цифры были бы шумом.

## Поиск по сайту

Кнопка в шапке, клавиша `/` (когда курсор не в поле ввода) или Ctrl/⌘+K открывают окно поиска: герои, предметы и разделы сайта (стрелки, Enter, Esc). Для игроков запрос превращается в действие — «открыть профиль» (Account ID, SteamID64, ссылка Steam) или «искать по нику»: длинное число (6–12 цифр) дополнительно предлагает «открыть матч» — номер матча и Account ID выглядят одинаково, поэтому показаны оба варианта; **к API игроков запрос уходит только после выбора**. Список героев — тот же кеш, что у главной; каталог предметов (тяжёлый) подгружается, только когда набрано два символа. Код окна — отдельный файл, подгружается заранее в паузе.

## «Мой профиль» и ранги

Account ID запоминается в `localStorage` (`dlhub_profile`): кнопка «Это я» на странице игрока либо ввод ID/ссылки на `/me`. Аккаунта и входа на сайте нет, ничего не уходит с устройства. `/ranks` — один запрос `/v1/players/rank/distribution` (3 КБ) и, если профиль выбран, ещё один — текущий ранг игрока (`services/rankDistributionService.js`: «лучше, чем у N% игроков»).

**Чего сайт не делает и почему.** Лидерборд сезона с очками лестницы невозможен на этом API: `/v1/leaderboard/{region}` отдаёт только ник, место и героев (параметр `leaderboard_id` ничего не меняет, очков нет). Вход через Steam (OpenID) не реализован: проверить его без ввода настоящих учётных данных нельзя, а непроверенный вход на сайте хуже его отсутствия.

## Профиль игрока: разбор, форма, напарники, картинка

На странице игрока (`/player/:id`) под цифрами идёт якорная навигация (как у героя) и пять разделов. Источников данных три, и у каждого своя надёжность, поэтому они не смешиваются:

| Источник | Что даёт | Чем ограничен |
|---|---|---|
| `match-history` (Steam) | полная и свежая история матчей: герой, итог, KDA, режим, бейдж ранга | у записи есть режим игры (`game_mode`: 1 — обычный, 4 — Street Brawl), поэтому Street Brawl и матчи с ботами из статистики и формы исключаются (`isStatsMatch`) |
| `players/hero-stats`, `mate-stats`, `enemy-stats` | суммы по героям, напарники и соперники | считаются только по матчам, которые приняла аналитика API: у проверенного игрока это 688 из 799 матчей (86%), у других может быть меньше; поэтому над напарниками написан **охват** |
| `analytics/hero-stats` на диапазоне рангов игрока | мета: винрейт каждого героя на его ранге | 30 дней, ранг игрока и по одному соседнему тиру (`rankBand`): на одном тире выборка узкая |

- **Разбор** (`services/playerInsightsService.js`, `components/player/PlayerAdvice.jsx`). Результаты игрока на каждом герое за последние 90 дней сравниваются с метой его ранга. Вывод «сильнее» или «слабее» делается, только если на герое не меньше 8 матчей, отклонение не меньше полутора стандартных (z ≥ 1,5, шанс случайности около 7%) **и** не меньше трёх пунктов; всё остальное — «на уровне». Рядом показаны «лишние победы» (сколько побед сверх того, что набрал бы средний игрок на этом герое за столько же матчей) и сглаженный винрейт. «Стоит попробовать» — герои, на которых игрок почти не играл (не больше двух матчей за период), с винрейтом не ниже 50% на его ранге (и не меньше 200 матчей в мете) и той же ролью или типом оружия, что у героев, где у игрока получается (а если таких нет — у самых играемых); это подсказка по двум признакам, а не прогноз. Игрок, который не играл больше 90 дней, получает пояснение, а не пустой блок. Запрос один — hero-stats на диапазон рангов, и только когда блок подошёл к экрану и у игрока есть хотя бы один герой с пятью матчами.
- **Форма** (`services/playerHistoryService.js`, `PlayerForm.jsx`). Серия побед или поражений (плашка от трёх подряд), полоса последних 20 результатов, скользящий винрейт в окне из 10 матчей (кривая появляется с 15 матчей) и ход ранга по рейтинговым матчам (`ranked_display_badge`). Слова «в росте» и «в спаде» ставятся, только если винрейт последних 20 матчей отличается от предыдущих 20 заметнее случайных колебаний (z-критерий для двух долей, z ≥ 1,28); иначе — «без перемен». Новых запросов нет: всё из загруженной истории. Под ними — свёрнутый блок **«Ход матча»** (`services/curveService.js`, `PlayerCurve.jsx`): `analytics/player-performance-curve` отдаёт средние души, убийства, смерти и помощь на каждой десятой доле матча за 90 дней; рядом строится такая же кривая для диапазона рангов игрока (без фильтра по игроку), и видно, раньше или позже среднего игрока ранга у него растёт число душ. Это матчи из аналитики API, а не вся история, и запрос тяжёлый (кривая ранга считается секунды), поэтому он уходит только по раскрытию блока (2 запроса).
- **Напарники и соперники** (`services/matesService.js`, `PlayerCircle.jsx`): `mate-stats` и `enemy-stats` с `min_matches_played=3` (30 и 3 КБ вместо сотен), `wins` в обоих ответах — победы **самого игрока** в совместных матчах (проверено по истории: 535 строк из 535). «Немезида» — соперник с самым большим перевесом над игроком (поражений минус побед), при четырёх и более встречах и перевесе не меньше двух. Параметр `same_party` не используется: он опирается на список друзей Steam и у игрока с закрытым списком возвращает пустоту. Имена — одним пакетным запросом `players/steam`.
- **Картинка для публикации** (`services/shareCardService.js` — что написано, `components/player/shareCardCanvas.js` — рисование). Карточка 1200×630: аватар, ник, ранг, четыре главных числа, три любимых героя и последние 10 результатов; рисуется на `canvas` в браузере посетителя по кнопке, скачивается PNG или копируется в буфер обмена. Аватар (`*.steamstatic.com`), значок ранга (`api.deadlock-api.com`) и иконки героев (`assets-bucket.deadlock-api.com`) отдают `Access-Control-Allow-Origin: *`, поэтому холст остаётся «чистым» и его можно сохранить; если картинка не загрузилась, рисуется заглушка. На сервер ничего не уходит. Размеры текста подгоняются под ширину (`fitText`).
- **Избранное и сравнение.** Звезда на странице игрока и героя кладёт его в `favoritesStore` (`dlhub_favorites`, до 12 игроков и 60 героев; всё, что читается из `localStorage`, проходит через `normalizeFavorites`). `/favorites` показывает карточку игрока со сводкой последних матчей (`fetchPlayerCard`: тот же запрос, что у истории, но в кеш уходит лишь сводка в сотни байт) и героев с текущей статистикой. `/versus?a=&b=` собирает два профиля теми же запросами и из того же кеша, что страница игрока, и сравнивает ранг, винрейт, KDA, точность, форму и общих героев; «впереди» не ставится, если разница меньше шума, и вообще не ставится у числа матчей и даты последнего: «больше» не значит «лучше».

**Чего нет и почему: история места в лидерборде.** Озеро данных (`data.deadlock-api.com`) хранит почасовые снимки лидерборда, но: (1) в них нет Account ID, только ник (`account_name`, может быть пустым и повторяться), поэтому надёжно сопоставить игрока нельзя; (2) живёт один снимок, а предыдущие уходят в `retired` — в манифесте их около суток; (3) снимок — 14 МБ (по героям — 66 МБ), для чтения в браузере нужны Parquet-ридер и новые исключения в CSP и CORS. Настоящая история места потребует собственного хранилища, в которое по расписанию (Vercel Cron) складываются снимки, — а своего сервера у сайта нет. Ближайшее честное, что есть сейчас, — график ранга по рейтинговым матчам игрока (раздел «Форма»).

## Эфир, прицел и калькулятор

- **Эфир** (`/live`, `services/liveService.js`, `hooks/useLiveMatches.js`). `matches/active` — вкладка «Смотреть» игры: не больше 200 матчей, в основном заметных, API обновляет их раз в две минуты, поэтому это витрина, а не все идущие матчи. `matches/live/urls` — адреса трансляций: **это поток для программ, читающих демо (demofile, haste), а не страница для браузера**, поэтому сайт его только показывает и копирует, ссылкой не делает (браузеру открывать там нечего: адрес `http://`, а отвечает он потоком данных). Совпадают списки лишь частично (при проверке — 12 адресов из 59 относились к матчам из витрины), поэтому остальные трансляции вынесены в свёрнутый блок. Души команд в Street Brawl — одинаковые заглушки, перевес там не показывается, а в остальных режимах разница меньше 1% считается «поровну». Фильтры (режим, регион, герой, порядок, только с трансляцией) лежат в адресе; список обновляется сам раз в 2 минуты, только пока вкладка видна. Кеш: ответы живут минуту (`vercel.json`), в `localStorage` не пишутся. Имена игроков карточки — один пакетный запрос по нажатию «Игроки».
- **Студия прицела** (`/crosshair`, `services/crosshairService.js`, `api/crosshairApi.js`). Картинку (`crosshair/settings/image`, PNG с прозрачным фоном «пиксель в пиксель» для выбранной высоты экрана) и код (`crosshair/settings/code`, обратно — `crosshair/code/settings`, понимает и команды консоли вида `citadel_crosshair_dot_size 4`) делает сам API; сайт собирает запросы и ждёт 350 мс после последнего движения ползунка. Настройки по умолчанию в коде равны тому, что API отдаёт для кода без параметров (тест сверяет их со снимком ответа). API принимает любые целые от 0 до 255 (проверка есть только у цветов), а пределы игры нигде не опубликованы, поэтому ползунки рассчитаны на привычные значения, а в числовое поле можно ввести другие. Картинка не умеет рисовать «прицел героя» (`themed`), поэтому при этом переключателе остаётся предпросмотр самих настроек — об этом написано на странице. Ответы кешируются на краю сутки.
- **Калькулятор билда** (`/calculator`, `services/calculatorService.js`). Это **оценка по данным игры**, а не копия её формул: здоровье = базовое + прирост за уровень × (уровень − 1) + плоское здоровье предметов; урон пули = (базовый + прирост × (уровень − 1)) × (1 + сумма «Weapon Damage»), умноженный на число пуль в выстреле; скорострельность и магазин меняют «Fire Rate» и «Max Ammo»; DPS «с перезарядками» считается тем же правилом, что у API. Что бонус постоянный, а что условный, говорят сами данные предмета: свойство из раздела `innate` без пометки `ConditionallyApplied` — постоянное, остальное (пассивки, активки, «при здоровье выше 65%») — условное; таблица показывает «без предметов», «с постоянными бонусами» и «если условия выполнены». Эффекты, которые калькулятор не считает (процент к базовому и максимальному здоровью у Colossus и Glass Cannon), перечисляются в «не учтено», а не пропадают. **Как проверено:** на 1-м уровне без предметов урон выстрела, DPS и DPS с перезарядками совпадают с готовыми цифрами `weapon_info` API у героев всех типов оружия (у оружия с очередями поправка на время цикла берётся из тех же цифр API); суммарный прирост урона пули за 35 уровней у 39 героев — от +50% до +203% базового (медиана +98%), что согласуется с «плоским приростом за уровень» и общим замыслом «урон удваивается к концу игры». **Допущения, которые нельзя проверить по данным:** уровень L даёт L − 1 «бонусов»; предел 36 — по данным матчей герои заканчивают игру на 36-м уровне в 99% игр. Способности, урон Духа, особенности героев, срабатывания предметов и предметы Брокера не учитываются. Состояние калькулятора — в адресе (`?hero=&lvl=&items=`, всё проверяется), каталог предметов (`slimCalcItems`) кладётся в кеш в облегчённом виде.

## Страница матча

`/match/:id` — итоги одного матча (`pages/MatchPage.jsx`, `components/match/*`, логика в `services/matchService.js`). Открывается из истории матчей игрока (вся строка — ссылка; `?p=<Account ID>` подсвечивает его строку, а «назад» ведёт в его профиль), из окна поиска (длинное число предлагает и игрока, и матч: у номера матча и Account ID одинаковый вид) или по ссылке. Страница закрыта от индексации и не входит ни в sitemap, ни в пререндер.

**Данные и запросы.** Матч — один запрос `GET /v1/matches/{id}/metadata`, около **мегабайта** (траектории игроков, матрицы урона, сотни полей статистики). `slimMatch` оставляет нужное — итоги, срезы души, журнал предметов, смерти, — и в кеш `localStorage` матч попадает размером ~14 КБ на неделю (матч не меняется). Имена и аватары игроков — **один пакетный запрос** `players/steam?account_ids=…` (кеш на час); каталог предметов (общий с другими страницами, 6 часов) подгружается, когда таблица уже на экране. Холодный заход — 2–3 запроса, повторный — 0.

**Что учесть.**

- В данных команды называются 0 и 1, названий сторон нет: на сайте это «Команда 1» (янтарная) и «Команда 2» (голубая). Объект принадлежит одной команде, а разрушает его соперник — в итогах объекты считаются у разрушившей.
- Журнал предметов вперемешку содержит покупки и очки способностей. Покупками считаются записи, чей предмет есть в каталоге улучшений (`splitItemLog`); порядок прокачки способностей не показывается.
- Срезы статистики идут раз в 3–5 минут, поэтому график перевеса по душам — это форма игры, а не поминутная хроника. Шкала симметрична, пока матч шёл вровень; если один соперник вёл всё время, пустая сторона сжимается (`leadRange`).
- Средний ранг команды считается по рейтингу игроков до матча (`teamAverageBadge`): собственное поле API `average_badge_team*` в ответе нулевое.
- У API нет ответа «матч не найден»: на несуществующий номер оно отвечает **503** («не удалось получить из Steam»). Поэтому на любую 5xx страница пишет, что номер мог быть неверным, а матч — слишком свежим или старым, и предлагает повторить (`matchErrorKey`).

## Обновления игры

Всё, что связано с текущим крупным обновлением, лежит в одном файле — `src/data/updates.js`. **Когда выходит новое большое обновление, править нужно только его** (и тексты карточек в локалях):

| Поле | Что делает |
|---|---|
| `CURRENT_UPDATE.name`, `date` | Название и дата: подпись в фильтре «С патча» и срок показа блока «что нового» (`highlightsDays`, 90 дней) |
| `heroIds` | Герои из голосования этого обновления — по ним строится полоса «Новые герои» |
| `releases` | Расписание выхода героев (часовой пояс, дни недели, час, дата первого релиза); отсчёт учитывает переход на летнее время |
| `highlights` | Карточки «что нового» на `/update`; тексты — в локалях (`update.highlights.<key>`), `to` — раздел сайта, куда ведёт карточка |
| `art` | Арты баннера и плитки патча на главной (пути в `public/art`); пока обновление свежее (`highlightsDays`), они показываются, потом баннер становится обычным. Замените файлы и пути на арты нового обновления (см. «Оформление и арты») |
| `OFFICIAL_UPDATE_URL` | Корень playdeadlock.com — он сам перенаправляет на страницу последнего обновления, поэтому ссылка не устаревает |

Последний патч, статус героев, карта, предметы сайт берёт из API сам. Страницу playdeadlock.com **нельзя встроить в iframe** — сервер Valve отдаёт `X-Frame-Options: SAMEORIGIN`, поэтому на `/update` выводятся анонс и заметки из Steam, а полная страница открывается кнопкой.

Внешний HTML (заметки Steam) не вставляется через `dangerouslySetInnerHTML`: `services/sanitize.js` разбирает его через `DOMParser` по белому списку тегов и собирает React-элементы; ссылки `linkfilter` разворачиваются, картинки допускаются только с `*.steamstatic.com`. Так же, отдельным компонентом, выводятся описания способностей на странице героя — подробности в разделе «Безопасность».

### Герои до выхода

`heroStatus()` (`api/heroApi.js`) делит героев на `released`, `upcoming` и `hidden`: вышедший — это герой с матчами либо доступный игрокам; `upcoming` — флаг `prerelease_only`. У героев, которых ещё нет в игре, в данных лежат **заготовки** (780 здоровья, оружие Infernus), поэтому цифры по ним не показываются. Как только появляются матчи и настоящий портрет, кружок на карточке «Новые герои» сам меняет стикер голосования на портрет; список героев обновляется раз в 4 минуты (с перепроверкой на сервере), так что выход подхватывается без перезагрузки страницы.

## Карта

`/map` строится из `GET /v1/assets/map` (цели, зиплайны, лагеря, интерактивные сущности, адреса картинок), `GET /v1/assets/misc-entities` (время появления лагерей и ящиков — для шкалы времени и подсказок) и — для слоя «Тепловая карта» — из `GET /v1/analytics/kill-death-stats`. Ответы приводятся к облегчённому виду (`services/mapService.js → slimMap`, `slimTimers`, `slimHeat`), все координаты — относительные (0..1).

- **Слои и пресеты** описаны в `mapService.js` (`LAYERS`, `PRESETS`). Состояние карты живёт в адресе: `/map?preset=new` — готовый вид, `/map?layers=objectives,ziplines` — свой набор, `&level=under` — уровень, `&t=480` — время матча; ссылкой можно поделиться, значения по умолчанию в адрес не попадают (`searchForState`). Слой с флагом `isNew` получает значок «NEW», на нём построен пресет «Что нового». У каждой группы слоёв есть кнопки «все / нет», над списком — счётчик показанных объектов.
- **Векторная основа.** Миникарта в API — картинка 1024×1024, и при приближении она превращалась в кашу. `services/mapTrace.js` вынимает из неё контуры: «marching squares» по прозрачности (улицы нарисованы полупрозрачным чёрным, здания и пустота прозрачны), подпиксельная точность по значениям соседних пикселей, упрощение ломаной (Рамер — Дуглас — Пейкер) и путь SVG: линии остаются чёткими на любом масштабе (в сборке не лежит ни одной картинки карты, как и раньше). Трассировка — около 60 мс на улицы и 30–80 мс на слой туннелей, результат хранится в памяти страницы. Порог улиц берётся по плато плотности (`plateauLevel`), порог туннелей — по доле картинки (`coverageLevel`): коридоры лежат на мягком ореоле той же краски. С новой картой в игре контуры перестраиваются сами. Картинка читается через canvas (`api/mapTraceApi.js`): хранилище картинок отдаёт CORS на запрос с `Origin` (`crossOrigin="anonymous"`, CSP пропускает его через `img-src`). Не вышло (нет CORS, картинка недоступна) — карта остаётся на растровой миникарте, как раньше.
- **Значки маркеров** — официальные иконки миникарты из игры (хранилище картинок API: лагеря трёх тиров и хранилища, урны душ, магазины, цели, ящики, закуски, телепорты, статуи) и собственные белые значки для слоёв, которых там нет (колокола, Покровитель, турели базы, батуты, канаты, паровые люки, завесы, разломы, бонус на мосту). Список и размеры значков — `services/mapIcons.js`; значок лежит на тёмной подложке в кольце цвета слоя (у построек — цвет команды). Крупные маркеры — элементы DOM со значком в `background`; мелкие точки (ящики, статуи, закуски, люки) на canvas рисуются точками и с масштаба 2,2× превращаются в такие же значки.
- **Уровни.** Высота объекта (`position[2]` в ответе API) показывает, что он под землёй (`z < −20`: туннели и подвалы): у таких точек в облегчённой карте стоит `u: 1`, остальные поле не получают. Переключатель «Все / Улицы / Под землёй» скрывает лишнее; на подземном уровне улицы приглушены, а оба слоя туннелей включаются сами. Строки списка слоёв при этом остаются на месте (пустые приглушены), счётчики считают объекты выбранного уровня.
- **Время матча.** Кнопка «Что уже появилось» включает шкалу 0–40 минут: ползунок, «играть» (минута матча за секунду) и быстрые переходы к моментам появления. Объекты, которых к этому времени ещё нет (лагеря по тирам, хранилища, ящики и статуи), затемнены. Числа — из конфигурации игры (`misc-entities`): слабые лагеря 2:00, ящики и статуи 3:00, средние 5:00, сильные и хранилища 8:00; те же значения (первое появление и интервал) — в таблице «Таймеры спавна» и в подсказках маркеров. У усилений точек на карте нет — они только в таблице. Время живёт в состоянии страницы и попадает в адрес, когда ползунок остановился. Чего нет в ответе, того карта не показывает (`slimTimers` не подставляет числа); API не ответил — карта работает без шкалы.
- **Достопримечательности обновления** (Колокольная башня, Затопленная площадь) сопоставлены с лагерями по внутренним названиям (`LANDMARKS` в `mapService.js`). После следующей карты проверь, что названия лагерей не изменились.
- **Объекты в ответе API смещены** относительно миникарты (центр симметрии в 0.45, а не в 0.5) — `recenter()` возвращает их на место по их же симметрии; если API поправит смещение, поправка станет нулевой сама.
- **Зиплайны** — кубические сплайны: узлы (`P0`) и касательные в каждом узле (`P1` — входящая, `P2` — исходящая, векторами от узла); они превращаются в путь SVG. Ширина линий (как и контуров основы) делится на масштаб — линии не толстеют при приближении.
- **Производительность.** Крупные маркеры (до сотни) — элементы DOM, мелкие точки (ящики, статуи, закуски, люки; до тысячи) рисует один `<canvas>`: иначе каждый шаг масштабирования пересчитывал бы стили у сотен элементов. Вид (масштаб и сдвиг) хранится в `ref` и применяется прямо к DOM (`hooks/useMapViewport.js`), React карту при жестах не перерисовывает. В собранном сайте колесо, перетаскивание и приближение держат 60 кадров в секунду и при всех слоях сразу.
- **Управление:** колесо и щипок — масштаб, перетаскивание — сдвиг, двойной щелчок — приблизить; клавиши `+` `−` `0` и стрелки. Кнопки, клавиши, двойной щелчок и сброс переходят к нужному виду плавно (200 мс, повторное нажатие продолжает с цели предыдущего; без анимации при «уменьшить движение» в системе). Пока карта не приближена, вертикальный жест пальцем прокручивает страницу.
- **Тепловая карта** тянет 29 тысяч строк (2,3 МБ) только при включении слоя, складывает их в растр 168×168 клеток и кеширует ~200 КБ. Период и ранги берутся из общих фильтров, фаза матча (начало / середина / поздняя) — отдельный выбор.

## Оформление и арты

Оформление — «Путеводитель» по мотивам страницы обновления City Never Sleeps на playdeadlock.com: тёплый чёрный с зерном плёнки, кремовые бумажные рамки (карточки героев, портрет на странице героя, билет с отсчётом), наклейки-плашки с неровным краем (роли, названия разделов, активный пункт меню), оранжевая плашка на слове-акценте заголовка, пунктирные «маршрутные» линии и силуэт города над подвалом. Всё держится на переменных в `:root` (`index.css`):

| Что | Переменные |
|---|---|
| Поверхности | `--bg`, `--bg-deep` (шапка), `--panel`, `--panel-2`, `--teal`, `--olive`, `--brown` (цветные панели плиток), `--line` |
| Бумага | `--paper`, `--paper-2`, `--tan`, `--paper-ink` (текст на бумаге) |
| Акценты | `--acid` (основной, оранжевый; имя осталось от прежнего оформления), `--cyan` и `--sky`, `--amber` (жёлтый), `--green`, `--rose`, `--violet`, `--red` |
| Смысл | `--good`, `--neutral`, `--bad`: винрейт и изменения (на бумаге вместо них тёмные оттенки) |
| Шрифты | `--font-display` (Alegreya 900: заголовки), `--font-caps` (Oswald: подписи заглавными), `--font-ui` (Jost: текст), `--font-num` (Oswald: числа с цифрами одной ширины; список селекторов — блок «Числа» в конце `index.css`), `--font-code` (системный моноширинный: технические подробности ошибки) |
| Тени | `--elev-1`, `--elev-2`, `--elev-3` |

Два правила, которые легко сломать. Интерактивные элементы (кнопки, ссылки) **не получают `clip-path`**: он обрезает кольцо фокуса. Неровный контур рисуют только неинтерактивные наклейки, а плашка активного пункта меню — псевдоэлемент. И `font` в CSS сбрасывает `font-variant-numeric`: цифры Alegreya по умолчанию «старинные» (в заголовке «5 из 6» они выглядят как буквы), поэтому у каждого правила с `--font-display` рядом стоит `lining-nums`.

**Арты** лежат в `public/art` (WebP, около 630 КБ на всё; `tests/site-files.test.js` не даёт им распухнуть, проверяет, что каждый путь из кода существует и что в папке нет картинок, которые никто не использует). Это облегчённые копии картинок с официальных страниц обновлений на playdeadlock.com. **Права на них принадлежат Valve**; сайт неофициальный и говорит об этом в подвале. Арты героев из хранилища API (`background_image_webp`, 1–2 МБ на героя) намеренно не используются: они тяжёлые, а хранилище общее для всего сообщества.
- *City Never Sleeps* (текущее обновление, `data/updates.js`): название и табличка Major Update, постеры новых героев, фотография города, ночной город для баннера, карта, силуэт города для подвала.
- *Old Gods, New Blood* (прошлое обновление; оригиналы взяты с CDN Valve, а не из переводов на сторонних сайтах): сплэш-арты шести героев (`hero-*.webp`, `data/heroArt.js`) — постер под портретом на странице героя, а на страницах «Игроки» и «Мой профиль» по постеру дня; два постера Патронов на странице карты; вереница мелких крипов на странице 404 и на экране ошибки. Страницу патчноута из этого обновления сайт не показывает: берутся только картинки. Чтобы добавить постер другому герою, положите арт в `public/art` (до 120 КБ) и допишите строку в `HERO_POSTERS` (ключ — id героя в данных API).

Файлы лежат без хеша в имени, поэтому `vercel.json` отдаёт их с кешем в сутки (`max-age=86400`) и неделей `stale-while-revalidate`: замена картинки дойдёт до посетителей не позже чем за сутки. Когда выйдет следующее большое обновление, положите новые арты в `public/art` (сожмите: лимит файла — 120 КБ, папки — 400 КБ) и поменяйте `CURRENT_UPDATE.art` в `src/data/updates.js`.

## Деплой, SEO и ошибки

- **`vercel.json`** задаёт три вещи: какие адреса `/api` уходят в Deadlock API, какие страницы сайта существуют и какие заголовки получает каждый ответ (подробности и причины — в разделе «Безопасность»). Адреса `/api` перечислены поимённо (это ровно те запросы, что делает код сайта), страницы — списком маршрутов из `App.jsx`: прямые ссылки (`/hero/67`, `/map`, обновление страницы) открывают приложение, а несуществующий адрес получает настоящий 404. Ответы `/api/v1|v2/*` кешируются на краю Vercel (`s-maxage=600`, `stale-while-revalidate`; результат матча — неделю): к бесплатному API ходит не каждый посетитель, а раз в 10 минут на адрес. **Добавили новую страницу или новый запрос к API — допишите адрес в `vercel.json`:** тест `tests/vercel-config.test.js` сверяет конфиг с исходниками и сам подскажет, чего не хватает. После деплоя проверка: `curl -sI https://dead-hub.vercel.app/api/v1/assets/ranks | grep -i x-vercel-cache` — со второго раза должно быть `HIT`.
- **Заголовки страниц**: `hooks/usePageMeta.js` ставит `<title>`, описание, canonical, `og:*` и `twitter:*`; тексты лежат в локалях (`seo.<страница>`), для героя, предмета и игрока название берётся из данных. `<html lang>` следует за языком интерфейса (`Layout`).
- **Пререндер** (`scripts/prerender.mjs`, шаг `npm run build` после `vite build`): для каждого героя и предмета рядом кладётся копия `index.html` (`dist/hero/<id>.html` и `dist/hero/<id>/index.html`) с **собственными** заголовком, описанием, canonical и тегами превью и коротким текстом в `<noscript>` (имя, роль, лор / слот, цена, описание); `sitemap.xml` дополняется всеми адресами (~220). Тексты те же, что на клиенте (`seo.hero.*`, `seo.item.*`), поэтому после загрузки приложение просто подтверждает их. Пререндер — только на английском: язык интерфейса на сервере неизвестен. Стоит **два запроса к API на сборку**; если API недоступен, сборка не падает, а страницы остаются обычным SPA (в логе предупреждение). `SKIP_PRERENDER=1` пропускает шаг — так делает CI. `vercel.json` включает `cleanUrls`, чтобы `/hero/25` отдавал `hero/25.html`. **После деплоя проверь**: `curl -s https://dead-hub.vercel.app/hero/25 | grep -o "<title>[^<]*"` — должен быть «Warden — hero stats, builds and matchups…», а не общий заголовок; если общий — значит хост не сопоставил адрес с файлом, и это единственное место, которое нужно поправить.
- **Превью ссылок**: `public/og-image.png` (1200×630, до 300 КБ — это проверяет тест) снимается с вёрстки `scripts/og-image.html`: откройте файл в Chrome или Edge с диска, включите в DevTools размер 1200×630, сделайте снимок страницы и сожмите его в палитру на ~100 цветов. Менять картинку нужно только при смене слогана или оформления. Значки вкладки (`favicon.svg`, `favicon.ico`, `favicon.png`, `apple-touch-icon.png`) — шестиугольник с буквой D, как знак в шапке: растровые копии делаются из SVG. `public/robots.txt` разрешает обход (`/api` не закрыт: поисковику нужны данные, чтобы увидеть страницу), `public/sitemap.xml` — статичные разделы; при новом разделе добавь его и туда.
- **404 и ошибки**: адрес, которого нет в списке маршрутов `vercel.json` (`/wp-login.php`, `/hero/abc`, опечатка в разделе), получает настоящий статус **404**: Vercel отдаёт `dist/404.html` — оболочку приложения с заголовком «Page not found», `noindex` и текстом для читающих без JavaScript (`renderNotFound`, её пишет `scripts/prerender.mjs` при каждой сборке, и в CI тоже), а роутер показывает `NotFoundPage`. Исключение — адрес вида `/hero/999999`: он похож на настоящий, и о том, что героя нет, знает только API, поэтому сервер отдаёт 200, а страницы героя, предмета и игрока с ошибкой закрыты от индексации на клиенте (`noindex`) — иначе они считались бы «мягкими» 404. `components/layout/ErrorBoundary.jsx` вместо пустого экрана показывает сообщение, меню остаётся на месте, при переходе на другую страницу ошибка сбрасывается.
- **Ежедневный деплой**: страницы героев и предметов пререндерятся при сборке, поэтому новый герой (по вторникам и пятницам) получает свою страницу и запись в sitemap только после нового деплоя. `.github/workflows/redeploy.yml` просит Vercel пересобрать проект через Deploy Hook: в 22:30 UTC по вторникам и пятницам (релиз в 14:00 по тихоокеанскому времени — это 21:00 или 22:00 UTC) и раз в сутки. Настройка (один раз): в Vercel — Project → Settings → Git → **Deploy Hooks** → создать хук для ветки `main`, скопировать адрес; в GitHub — Settings → Secrets and variables → Actions → **New repository secret** с именем `VERCEL_DEPLOY_HOOK` и этим адресом. Без секрета workflow ничего не делает (в логе — пометка), с неверным адресом — падает. Запустить вручную можно во вкладке Actions («Run workflow»). GitHub выключает расписания в репозитории без активности 60 дней, а запуски иногда запаздывают на минуты.
- **Доступность**: цвет `--dim` даёт контраст ≥4,5:1, текст не мельче 11 px, закрытое мобильное меню скрыто (`visibility`) и не перехватывает Tab.

### Бюджет запросов к API

API бесплатный и с лимитом, поэтому: список героев перепроверяется раз в 4 минуты только в «окно релиза» (минуты вокруг расписания Valve, `isReleaseWindow`), в остальное время — раз в 30 минут; таймер полосы «Новые герои» (главная и список героев) сам ничего не запрашивает; карта и тепловая карта держатся в кеше 6 и 3 часа, а смена фильтров тепловой карты ждёт 300 мс; способности героя берутся из списка `by-hero-id`, а не 4 отдельными запросами; ранги выбираются готовым диапазоном (один набор запросов вместо двух).

Что стоит каждая возможность (запросов к API, холодный кеш; повторно — из кеша браузера и с края Vercel):

| Что | Запросы |
|---|---|
| Главная | список обновлений, справочник героев, hero-stats — 3 (без Δ и названий рангов: панели фильтров на ней нет) |
| Список героев (`/heroes`) | те же, названия рангов (панель фильтров) и hero-stats прошлого периода (Δ) — 5 |
| Мета | те же, что у списка героев (из кеша) |
| Страница героя | герой, способности, оружие, hero-stats (из кеша), counter+synergy, сборки (2) и Δ (из кеша); динамика — +1, только когда блок подошёл к экрану |
| Предметы (`/items`) | каталог (общий, 6 часов); магазин на широком экране — ещё 2: `item-stats` на все предметы и `item-stats?bucket=hero` для панели (оба общие со страницей предмета, кеш 10 минут); сетка — 0 запросов статистики, пока не выбрана сортировка по цифрам; таблица — те же, что магазин |
| Случайный билд | 0 новых: каталог предметов и список героев из кеша; +1 `item-stats` на героя только при включённом «без бесполезных» (общий со страницей героя) |
| Поиск | 0 при кеше; каталог предметов — 1 при наборе двух символов; игроки — только после выбора |
| Тир-лист по данным | 0 (hero-stats и Δ из кеша) |
| Помощник драфта | 0 новых (матрицы матчапов и hero-stats — те же, что у `/matchups`) |
| Страница матча | 2–3: матч (~1 МБ, дальше ~14 КБ из кеша на неделю), пакет профилей игроков, каталог предметов (если его нет в кеше) |
| Ранги | 1, с «моим профилем» — 2 |
| Страница игрока | 4 сразу (профиль Steam, ранг, история, hero-stats игрока); разбор — +1 (hero-stats на ранг игрока, когда блок подошёл к экрану и есть герой с пятью матчами); напарники — +2 и имена +1 (тоже при подходе к экрану); «Ход матча» — +2 по раскрытию блока (кривая игрока и кривая ранга); картинка — до 5 картинок с CDN, только по кнопке |
| Эфир | 2 (`matches/active`, `matches/live/urls`) и общий список героев (из кеша; холодный — +2), дальше раз в 2 минуты на открытой вкладке; имена игроков карточки — 1 по нажатию «Игроки» |
| Студия прицела | 2 при открытии (картинка и код), потом по 2 через 350 мс после последнего изменения; повторы настроек приходят с CDN (ответы живут на краю сутки) |
| Калькулятор | общий список героев (из кеша; холодный — +2), 1 каталог предметов (~460 КБ в сжатом виде, в кеш уходит облегчённый) и 2 на героя (герой и оружие; из кеша, если открывали страницу героя) |
| Сравнение игроков | как две страницы игрока (4 + 4, из кеша, если их открывали) и общий список героев; поиск по нику — 1 |
| Карта (`/map`) | 2: `assets/map` (~110 КБ, ~20 КБ в сжатом виде, в кеш уходит ~30 КБ) и `assets/misc-entities` (4 КБ, ради таймеров: упал — карта работает без шкалы времени); контуры берутся из трёх картинок хранилища (не API); слой «Тепловая карта» — +1 (2,3 МБ, в кеш ~200 КБ) |
| Сравнение героев | 0 новых: общий список героев (из кеша; холодный — +2) |
| Избранное | общий список героев (для героев и значков) и 1 на игрока (история матчей; в кеш уходит только сводка), только для карточек, дошедших до экрана |
| Сборка (пререндер) | 2 |

Лимит API — 200 запросов в минуту на IP, а все посетители идут через один адрес Vercel: поэтому кеш на краю (`s-maxage=600`) важнее кеша браузера. Своего бэкенда с историей по дням у сайта нет — недельную динамику даёт сам API (`bucket=start_time_week`).

Когда API всё-таки отказывает, `httpClient` бережёт и лимит, и посетителя: у каждого запроса таймаут 30 с; **устаревшая запись кеша не выбрасывается, а остаётся запасной** (до недели): при таймауте, сбое сети, 5xx и 429 страница покажет прежние данные вместо ошибки (не при 400 и 404: они говорят «такого нет», и старые данные скрыли бы правду), и каждый такой откат оставляет в консоли предупреждение `[dlhub] API не ответил…` с причиной и временем сохранения данных (иначе вчерашние данные на экране выглядят как ошибка сайта: например, у вышедшего героя всё ещё стикер голосования вместо портрета); после ответа 429 клиент на время из `Retry-After` (5–120 с, по умолчанию 30) вообще не обращается к API — лимит общий для всех посетителей, лишние запросы только продлили бы отказ.

## Безопасность

**Внешний HTML.** Заметки Steam и описания способностей приходят от сторонних сервисов, поэтому нигде не вставляются как есть. `RichHtml` (заметки) и `TooltipHtml` (описания на странице героя) разбирают строку через `DOMParser` — он строит «мёртвый» документ, где скрипты не выполняются и картинки не грузятся — и собирают из дерева новые элементы React. Что пропускать, решают чистые правила в `services/sanitize.js`; `dangerouslySetInnerHTML` запрещён линтером (`react/no-danger`). Раньше описания способностей вставлялись как есть: подмена ответа API на `<img onerror=…>` исполнялась и оседала в кеше `localStorage`.

- **Теги описаний:** `span`, `br`, `b`/`strong`/`i`/`em`/`u`, значки `img` и иконки SVG (`svg`, `g`, `path`, `rect`, `defs`, `clipPath`, простые фигуры). Неизвестные теги (в данных встречается служебный `<Panel>` из интерфейса игры, его никто не закрывает) разворачиваются — остаётся то, что внутри. Опасные (`script`, `style`, `iframe`, `object`, `form`, `math`, `template`…) и любые чужие элементы внутри SVG (`foreignObject`, `use`, `image`, `a`, `animate`…) выбрасываются вместе с содержимым.
- **Атрибуты** — только перечисленные и только с проверенными значениями. Класс — из известных (`highlight`, `diminish`, `inline-attribute-label` и название свойства после него): чужое имя могло бы включить правила CSS самого сайта, например наложение на всю страницу. Стиль — только `color: #hex`. У SVG — размеры, `viewBox`, цвета без `url()`, данные пути из набора символов `M L H V C Z…`, `transform` только из функций преобразования. Значок `img` — только https с `assets-bucket.deadlock-api.com/assets-api-res/images/`, без логина в адресе. Обработчики событий, `href`/`xlink:href`, прочие `style` и `xmlns` не переносятся никогда.
- **Идентификаторы SVG** получают префикс экземпляра, а ссылки `clip-path="url(#…)"` ведут только на элементы того же описания: раньше одинаковые `clip0_…` в разных описаниях (у Abrams их два) ссылались друг на друга.
- **Ссылки в заметках Steam** — только `https` и без логина с паролем в адресе (`https://steamcommunity.com@evil.example/` ведёт на evil.example), `rel="noopener noreferrer nofollow"`; картинки — только `*.steamstatic.com`.
- **Пределы:** строка длиннее 40 000 знаков обрезается, вложенность — 12 уровней, до 1 500 узлов на описание (в настоящих данных — до 9 000 знаков, 5 уровней и 25 узлов).
- **Тесты:** `tests/sanitize.test.js` проверяет правила, `tests/tooltipHtml.test.js` — всю цепочку «строка → DOM → элементы React → разметка» в jsdom. 8 настоящих описаний (`tests/fixtures/ability-descriptions.json`, по одному на каждую разновидность разметки, есть русское) сохраняют текст, классы, цвета и иконки, а 41 атакующая строка не оставляет в разметке ни скрипта, ни обработчика, ни ссылки наружу. Сами тесты проверены «мутациями»: если намеренно сломать правило (пропустить любой адрес картинки, вернуть класс как есть, убрать префикс id…), они краснеют.

**Хранилище браузера.** `localStorage` бывает недоступен (Chrome «блокировать все cookie», страница в sandbox-окне без `allow-same-origin`): чтение бросает `SecurityError`. Все обращения к нему обёрнуты в `try/catch`, включая чтение языка при запуске: без этого падал весь бандл, и вместо сайта оставался белый экран (`tests/heroStore.test.js`; проверено и в настоящем браузере в sandbox-окне — до исправления модуль не загружался, после загружается и стартует на английском). Без хранилища сайт работает, просто ничего не запоминает.

**Секреты и зависимости.** Сайту не нужны ни ключи, ни переменные окружения; `.env` не отслеживается git (`.gitignore`), шаблон — `.env.example`. Токен CI только читает репозиторий (`permissions: contents: read`), Dependabot раз в неделю присылает pull request на обновления npm и GitHub Actions: мелкие — одним, мажорные — по одному пакету, но связанные пакеты (React с `react-dom` и типами, Vite с плагином) — одним PR на всех, потому что поодиночке они не ставятся (npm ERESOLVE). Мажорные ESLint (`eslint`, `@eslint/js`) отключены, пока `eslint-plugin-react` не поддерживает десятую версию — правила и причина описаны в `.github/dependabot.yml`. `npm audit` — 0 уязвимостей: React Router обновлён до v7 (замечания v6 касались редиректа через обратный слэш и SSR-гидратации; здесь они не эксплуатировались, но теперь закрыты).

**Граница с API.** Раньше `/api/*` проксировался целиком: через наш домен можно было вызвать любой метод апстрима (в том числе тяжёлые и закрытые), а чужие сайты — читать его из браузера своих посетителей (`Access-Control-Allow-Origin: *`). Теперь `vercel.json` пропускает только то, что запрашивает код сайта: адреса перечислены поимённо, числовые id — только цифры, регионы лидерборда — из списка; всё остальное под `/api` отвечает 404. Заголовок CORS у ответов — только адрес самого сайта (ему CORS не нужен: запросы идут с того же адреса). Результат матча кешируется на краю неделю — он не меняется, — остальное по-прежнему 10 минут. В браузере всё это живёт не дольше минут: в том же заголовке приходит и ответ-ошибка, и надолго запоминать её нельзя.

- **Как это проверяется.** `tests/vercel-config.test.js` прогоняет конфиг через `@vercel/routing-utils` — тот самый разбор, который делает Vercel при деплое, — и сверяет его с кодом: адреса запросов берутся из `src/api/*.js`, страницы — из `App.jsx`. Все адреса сайта должны уходить в апстрим без искажений, а запретные (`/api/v1/sql`, `…/players/<id>/card`, лишние сегменты, нецифровые id, `..%2F`) — нет; каждая страница — открываться, а любой другой адрес — получать 404; на каждый ответ — ровно по одному правилу `Cache-Control`, чтобы правила не перебивали друг друга. Новый запрос или маршрут без записи в `vercel.json` роняет тест с подсказкой. Тесты проверены «мутациями» конфига (вернуть открытый прокси, забыть страницу, добавить `unsafe-inline` скриптам…) — на каждую они краснеют.
- **Зачем `overrides` в `package.json`.** У `@vercel/routing-utils` (только для тестов) зафиксирована версия `path-to-regexp` с известным замечанием о катастрофическом разборе шаблонов. Мы разбираем только свой конфиг, но `npm audit` ругался бы; поэтому версия заменена на исправленную 6.3.0 — маршруты для нашего конфига получаются побайтно те же, что у версии Vercel.
- **Ограничение частоты настраивается вручную** (в репозиторий оно не кладётся): Vercel → проект → **Firewall** → Custom Rules → правило «Request Path начинается с `/api/`» → Rate Limit, например 120 запросов в минуту на IP (холодная загрузка страницы героя — около 12), действие Deny или 429. Допустимые параметры можно варьировать (например, `min_unix_timestamp=…`), и каждое новое значение — промах кеша и запрос к апстриму: массово такое остановит только это правило. Если лимит API уже исчерпан атакой, включите Attack Challenge Mode.

**Заголовки и CSP.** Все ответы получают `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (камера, микрофон, геолокация, платежи, USB отключены) и `Cross-Origin-Opener-Policy: same-origin`. HSTS Vercel добавляет сам.

- **CSP:** скрипты, таблицы стилей, шрифты и запросы (`connect-src`) — только со своего адреса; `object-src 'none'`, `frame-ancestors 'none'`, `base-uri` и `form-action` — только свой адрес. Картинки — со своего адреса, `data:` (одна стрелка в CSS), хранилища ассетов API (`assets-bucket.deadlock-api.com`: портреты, иконки предметов, карта), самого API (`api.deadlock-api.com`: значки подрангов приходят адресом `…/v1/assets/ranks/<ранг>/<подранг>/image`, не из хранилища) и CDN Steam (`*.steamstatic.com`: аватары и картинки новостей).
- **Атрибуты `style` разрешены** (`style-src-attr 'unsafe-inline'`), таблицы стилей и элементы `<style>` — нет. Причина: браузер сообщает о нарушении всякий раз, когда разбирает HTML с `style="color: …"`, а так разбираются описания способностей — даже в отдельном документе, где ничего не рисуется. Цвет затем ставится через CSSOM (React), поэтому на безопасность это не влияет: скрипты по-прежнему только свои.
- **Режим — запрет, не Report-Only:** отчёты некуда слать (своего приёмника нет, чужой не заводился), поэтому режим «только отчёты» ничего бы не сообщил. Вместо него политику прогнали в настоящем браузере на собранном сайте с заголовками из `vercel.json` (маршруты строила та же библиотека, что у Vercel) по всем страницам: нарушений нет, картинки, шрифты и данные грузятся. Это и стоило найденной ошибки: значки рангов брались с хоста API, которого в первом варианте политики не было. Теперь это закрыто тестом по снимку ответа `/v1/assets/ranks` (`tests/fixtures/ranks.json`).
- **Если на сайте пропала картинка или шрифт**, первым делом откройте консоль браузера: запрет CSP пишется туда («Refused to load…»). Новый внешний хост из кода тест заметит сам; хост, который появится только в данных API (как значки рангов), — нет: его нужно добавить в `img-src` вручную.

**Шрифты** раздаются самим сайтом (`src/fonts.css`, пакеты `@fontsource`, лицензия OFL), а не с Google Fonts: страница не обращается к чужим серверам, посетители не отдают им свои адреса (для сайтов с посетителями из ЕС это ещё и вопрос приватности), экономится два лишних соединения, и CSP может запретить всё, кроме своего адреса. Подключены целые начертания (`400.css`, а не `latin-400.css`): в них у каждого набора знаков задан `unicode-range`, и браузер скачивает только нужные (латиница, кириллица, греческая Δ…); у отдельных наборов его нет, и два подряд перекрыли бы друг друга. Файлы шрифтов не вшиваются в CSS (`vite.config.js`, `assetsInlineLimit`): CSS блокирует отрисовку, и вшитый шрифт скачивался бы всегда, а отдельный файл кешируется и грузится только когда нужен. Подключено 8 начертаний (Alegreya 900, Oswald 500/600/700, Jost 400/500/600/700); страница на русском скачивает около 120 КБ шрифтов, на английском — меньше.

**Что пока не закрыто:**

- Ограничение частоты настраивается вручную (см. выше) и без него не работает; нормализация параметров на краю (округление времени до суток, чтобы разные значения не плодили промахи кеша) потребовала бы функции перед кешем — пока не сделана.
- Адрес вида `/hero/999999` отдаёт 200: он похож на настоящий, а героя нет только по мнению API (закрыто `noindex` на клиенте).
- У CSP нет канала отчётов: о заблокированном ресурсе узнаёшь из консоли, а не из мониторинга.

## Размер ответов и кеш

Ответы API бывают большими (список героев — 1,8 МБ, предметов — 5,7 МБ), а `localStorage` — около 5 МБ. `httpClient.js` поэтому применяет `transform` **до записи в кеш**: в `localStorage` попадают только нужные поля (`slimHero`, `slimItem`, `slimMap`, `slimHeat`, `slimPatches`…). Ключи имеют префикс версии (`dlhub_v3_*`); при смене формата версию поднимают, а старые записи удаляются сами. Запись хранит время и срок жизни (`{"ts":…,"ttl":…,"data":…}`): при нехватке места первыми вытесняются записи, у которых этот срок вышел, — а не всё старше часа, как было, — затем самая старая треть; записи старше недели удаляются при чтении. Одинаковые параллельные запросы делят один `fetch`, у данных, которые меняются в известные моменты (список героев), включена перепроверка `cache: 'no-cache'`.

## Запуск

### Требования

- Node.js 22.12+ (или 24): этого требует Vitest 5

### Установка

```bash
git clone <repo-url>
cd deadlocker
npm install
```

### Переменные окружения

Сайту они не нужны: он всегда ходит на `/api` (на Vercel это rewrite из `vercel.json`, при `npm run dev` — прокси Vite). Прежние режимы `direct` и `backend` из кода убраны. Файл `.env` не отслеживается git (он в `.gitignore`), а в `.env.example` описаны две необязательные переменные сборки — `PRERENDER_API` и `SKIP_PRERENDER`. Если когда-нибудь понадобятся ключи, кладите их в `.env`, в шаблоне оставляйте только имена без значений.

### Dev-сервер

```bash
npm run dev
```

Vite проксирует `/api/*` → `https://api.deadlock-api.com`, CORS в локальной разработке не мешает.

### Сборка и деплой

```bash
npm run build    # сборка в dist/ + пререндер страниц героев и предметов
npm run preview  # локальный предпросмотр сборки
```

Предпросмотр сборки (`npm run preview`) отдаёт пререндеренные страницы по адресам вида `/hero/25`. Пререндер ходит в API (2 запроса); в CI и там, где сеть не нужна, — `SKIP_PRERENDER=1 npm run build`. Если Node не берёт прокси из окружения, добавь `NODE_USE_ENV_PROXY=1`.

### Проверки

```bash
npm run lint    # ESLint (ошибки, хуки React; стиль не навязывается)
npm test        # Vitest: чистая логика (src/services), локали (одинаковые ключи в EN и RU, все t() существуют), vercel.json, sitemap, пререндер, санитайзер
npm run check   # линтер + тесты + сборка — то же, что делает CI
```

Тесты не ходят в сеть: ответы API лежат в `tests/fixtures/` (снимки реальных ответов, урезанные до нужных полей). `.github/workflows/ci.yml` запускает линтер, тесты и сборку (`SKIP_PRERENDER=1`) на каждый push в `main` и каждый pull request. React-страницы целиком тестами не покрыты: логика вынесена в `services/`, а интерфейс проверяется вручную в браузере. Исключение — вывод внешнего HTML (`TooltipHtml`): его проверяют в jsdom (файл помечен `// @vitest-environment jsdom`, остальные тесты работают в Node).

Для деплоя на **Vercel**: подключи репозиторий — `vercel.json` уже настроен.

## Локализация

Сайт поддерживает **русский** и **английский**. Переводы в `src/i18n/locales/`. Для нового языка — добавь файл локали и зарегистрируй его в `src/i18n/index.js`.

## Архитектура и планы

Сейчас проект — SPA, которая ходит в публичный Deadlock API через `/api` (rewrite на Vercel, прокси Vite в dev). Логика нормализации данных живёт во фронте (`heroApi.js`, `heroService.js` и другие `services/`), своего бэкенда нет: недельную динамику даёт сам API, а повторные запросы разных посетителей гасит кеш на краю Vercel.

Если лимит бесплатного API начнёт мешать, следующий шаг — не отдельный бэкенд, а тонкий слой на краю Vercel: список разрешённых путей и параметров, ограничение частоты и кеш на срок, подходящий каждому ответу (результат матча не меняется никогда). Что именно не закрыто сегодня — в конце раздела «Безопасность».
