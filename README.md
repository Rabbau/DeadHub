# [Dead Hub](https://dead-hub.vercel.app/)

Фан-сайт сообщества для игры **Deadlock** (Valve) — справочник по героям, каталог предметов, матчапы (контрпики и синергии), профили игроков, лидерборд, интерактивная карта города, страница последнего обновления, сравнение, тир-лист и генератор случайного билда. Данные загружаются с [deadlock-api.com](https://deadlock-api.com).

## Технологии

| | |
|---|---|
| **Фреймворк** | React 18 + Vite 6 |
| **Роутинг** | React Router v6 |
| **Состояние** | Zustand 5 (persist для тир-листа и сравнения) |
| **Стили** | CSS (`index.css`) + clsx |
| **Деплой** | Vercel (Edge Functions + CDN) |
| **Планы** | React frontend + FastAPI backend (см. [CHECKLIST.md](./CHECKLIST.md)) |

## Страницы

| `/hero/:id` | Детальная страница героя: статы, матчапы, популярные билды, способности. У героя, которого ещё нет в игре, вместо цифр — пояснение |

## Фильтры статистики

Период и диапазон рангов (от Initiate до Eternus) — общие для всего сайта: панель `StatsFilters` есть на главной, мете, матчапах, страницах героя и предмета и на карте (когда включена тепловая карта). Выбор хранится в `localStorage` (`dlhub_filters`).

Период — это **«С патча»** либо 7 / 14 / 30 / 90 дней. Пока последнее обновление моложе 21 дня, по умолчанию выбрано «С патча»: окно «30 дней» наполовину состоит из данных до обновления (другие герои, предметы и карта). Время обновления берётся из ленты `/v2/patches` (новости Steam) и хранится прямо в фильтрах (`since`), поэтому адрес запроса и ключ кеша определяются самим объектом фильтров.

Статистика героев берётся из `GET /v1/analytics/hero-stats` — **одним запросом на всех героев**. Винрейт — доля побед героя, пикрейт — доля героя среди всех пиков выборки (сумма по героям 100%). Под панелью показан размер выборки: при узких фильтрах (высокие ранги, короткий период) цифры «шумят», и сайт об этом предупреждает.

Начало периода округляется до суток (UTC), чтобы адрес запроса не менялся каждую секунду — иначе не работал бы ни кеш браузера, ни CDN.

## Обновления игры

Всё, что связано с текущим крупным обновлением, лежит в одном файле — `src/data/updates.js`. **Когда выходит новое большое обновление, править нужно только его** (и тексты карточек в локалях):

| Поле | Что делает |
|---|---|
| `CURRENT_UPDATE.name`, `date` | Название и дата: подпись в фильтре «С патча» и срок показа блока «что нового» (`highlightsDays`, 90 дней) |
| `heroIds` | Герои из голосования этого обновления — по ним строится полоса «Новые герои» |
| `releases` | Расписание выхода героев (часовой пояс, дни недели, час, дата первого релиза); отсчёт учитывает переход на летнее время |
| `highlights` | Карточки «что нового» на `/update`; тексты — в локалях (`update.highlights.<key>`), `to` — раздел сайта, куда ведёт карточка |
| `OFFICIAL_UPDATE_URL` | Корень playdeadlock.com — он сам перенаправляет на страницу последнего обновления, поэтому ссылка не устаревает |

Последний патч, статус героев, карта, предметы сайт берёт из API сам. Страницу playdeadlock.com **нельзя встроить в iframe** — сервер Valve отдаёт `X-Frame-Options: SAMEORIGIN`, поэтому на `/update` выводятся анонс и заметки из Steam, а полная страница открывается кнопкой.

Внешний HTML (заметки Steam) не вставляется через `dangerouslySetInnerHTML`: `services/sanitize.js` разбирает его через `DOMParser` по белому списку тегов и собирает React-элементы; ссылки `linkfilter` разворачиваются, картинки допускаются только с `*.steamstatic.com`.

### Герои до выхода

`heroStatus()` (`api/heroApi.js`) делит героев на `released`, `upcoming` и `hidden`: вышедший — это герой с матчами либо доступный игрокам; `upcoming` — флаг `prerelease_only`. У героев, которых ещё нет в игре, в данных лежат **заготовки** (780 здоровья, оружие Infernus), поэтому цифры по ним не показываются. Как только появляются матчи и настоящий портрет, кружок на карточке «Новые герои» сам меняет стикер голосования на портрет; список героев обновляется раз в 4 минуты (с перепроверкой на сервере), так что выход подхватывается без перезагрузки страницы.

## Карта

`/map` строится из `GET /v1/assets/map` (миникарта, цели, зиплайны, лагеря, интерактивные сущности) и — для слоя «Тепловая карта» — из `GET /v1/analytics/kill-death-stats`. Ответ приводится к облегчённому виду (`services/mapService.js → slimMap`), все координаты — относительные (0..1).

- **Слои и пресеты** описаны в `mapService.js` (`LAYERS`, `PRESETS`). Набор слоёв живёт в адресе: `/map?preset=new` — готовый вид, `/map?layers=objectives,ziplines` — свой набор; ссылкой можно поделиться. Слой с флагом `isNew` получает значок «NEW», на нём построен пресет «Что нового».
- **Достопримечательности обновления** (Колокольная башня, Затопленная площадь) сопоставлены с лагерями по внутренним названиям (`LANDMARKS` в `mapService.js`). После следующей карты проверь, что названия лагерей не изменились.
- **Объекты в ответе API смещены** относительно миникарты (центр симметрии в 0.45, а не в 0.5) — `recenter()` возвращает их на место по их же симметрии; если API поправит смещение, поправка станет нулевой сама.
- **Зиплайны** — кубические сплайны: узлы (`P0`) и касательные в каждом узле (`P1` — входящая, `P2` — исходящая, векторами от узла); они превращаются в путь SVG.
- **Производительность.** Крупные маркеры (до сотни) — элементы DOM, мелкие точки (ящики, статуи, закуски, люки; до тысячи) рисует один `<canvas>`: иначе каждый шаг масштабирования пересчитывал бы стили у сотен элементов. Вид (масштаб и сдвиг) хранится в `ref` и применяется прямо к DOM (`hooks/useMapViewport.js`), React карту при жестах не перерисовывает.
- **Управление:** колесо и щипок — масштаб, перетаскивание — сдвиг, двойной щелчок — приблизить; клавиши `+` `−` `0` и стрелки. Пока карта не приближена, вертикальный жест пальцем прокручивает страницу.
- **Тепловая карта** тянет 29 тысяч строк (2,3 МБ) только при включении слоя, складывает их в растр 168×168 клеток и кеширует ~200 КБ. Период и ранги берутся из общих фильтров, фаза матча (начало / середина / поздняя) — отдельный выбор.

## Деплой, SEO и ошибки

- **`vercel.json`**: первым правилом идёт прокси `/api/*` → deadlock-api.com, вторым — запасной `index.html` для всех остальных адресов (SPA). Без него прямые ссылки (`/hero/67`, `/map`, обновление страницы) на Vercel отдавали 404. Ответы `/api/v1|v2/*` кешируются на краю Vercel (`s-maxage=600`, `stale-while-revalidate`): к бесплатному API ходит не каждый посетитель, а раз в 10 минут на адрес. После деплоя проверка: `curl -sI https://dead-hub.vercel.app/api/v1/assets/ranks | grep -i x-vercel-cache` — со второго раза должно быть `HIT`.
- **Заголовки страниц**: `hooks/usePageMeta.js` ставит `<title>`, описание, canonical, `og:*` и `twitter:*`; тексты лежат в локалях (`seo.<страница>`), для героя, предмета и игрока название берётся из данных. `<html lang>` следует за языком интерфейса (`Layout`). Сайт — SPA: боты соцсетей видят только общие теги из `index.html`.
- **Превью ссылок**: `public/og-image.png` (1200×630) делается скриптом `node scripts/generate-og-image.mjs` без зависимостей; менять его нужно только при смене слогана или цветов. `public/robots.txt` разрешает обход (`/api` не закрыт: поисковику нужны данные, чтобы увидеть страницу), `public/sitemap.xml` — статичные разделы; при новом разделе добавь его и туда.
- **404 и ошибки**: маршрут `*` показывает `NotFoundPage` (закрыта от индексации: сервер отдаёт для неё 200), `components/layout/ErrorBoundary.jsx` вместо пустого экрана показывает сообщение, меню остаётся на месте, при переходе на другую страницу ошибка сбрасывается.
- **Доступность**: цвет `--dim` даёт контраст ≥4,5:1, текст не мельче 11 px, закрытое мобильное меню скрыто (`visibility`) и не перехватывает Tab.

### Бюджет запросов к API

API бесплатный и с лимитом, поэтому: список героев перепроверяется раз в 4 минуты только в «окно релиза» (минуты вокруг расписания Valve, `isReleaseWindow`), в остальное время — раз в 30 минут; таймер на главной сам ничего не запрашивает; карта и тепловая карта держатся в кеше 6 и 3 часа, а смена фильтров тепловой карты ждёт 300 мс; способности героя берутся из списка `by-hero-id`, а не 4 отдельными запросами; ранги выбираются готовым диапазоном (один набор запросов вместо двух).

## Размер ответов и кеш

Ответы API бывают большими (список героев — 1,8 МБ, предметов — 5,7 МБ), а `localStorage` — около 5 МБ. `httpClient.js` поэтому применяет `transform` **до записи в кеш**: в `localStorage` попадают только нужные поля (`slimHero`, `slimItem`, `slimMap`, `slimHeat`, `slimPatches`…). Ключи имеют префикс версии (`dlhub_v3_*`); при смене формата версию поднимают, а старые записи удаляются сами. Одинаковые параллельные запросы делят один `fetch`, у данных, которые меняются в известные моменты (список героев), включена перепроверка `cache: 'no-cache'`.

## Запуск

### Требования

- Node.js 18+

### Установка

```bash
git clone <repo-url>
cd deadlocker
npm install
```

### Переменные окружения

Скопируй `.env.example` в `.env`:

```bash
cp .env.example .env
```

Доступные режимы API (`VITE_API_MODE`):

| Режим | Описание |
|---|---|
| `direct` | Прямые запросы к `deadlock-api.com` (подходит для GitHub Pages) |
| `vercel` | Запросы через `/api` (Vercel rewrites / Edge Function) |
| `backend` | Собственный FastAPI-бэкенд (`VITE_BACKEND_URL`) |

### Dev-сервер

```bash
npm run dev
```

Vite проксирует `/api/*` → `https://api.deadlock-api.com`, CORS в локальной разработке не мешает.

### Сборка и деплой

```bash
npm run build    # сборка в dist/
npm run preview  # локальный предпросмотр сборки
```

Для деплоя на **Vercel**: подключи репозиторий — `vercel.json` уже настроен.

## CORS-прокси (api/proxy.js)

Edge Function поддерживает два апстрима:

```
/api/proxy.js?path=assets/...    → https://assets.deadlock-api.com/...
/api/proxy.js?path=analytics/... → https://api.deadlock-api.com/...
```

Ответы кэшируются на Vercel CDN (`Cache-Control: s-maxage=3600`).

## Локализация

Сайт поддерживает **русский** и **английский**. Переводы в `src/i18n/locales/`. Для нового языка — добавь файл локали и зарегистрируй его в `src/i18n/index.js`.

## Архитектура и планы

Сейчас проект — SPA, которая ходит напрямую (или через прокси) в публичный Deadlock API. Логика нормализации данных живёт во фронте (`heroApi.js`, `heroService.js`).

В будущем планируется переход на **React + FastAPI**:

- фронт остаётся тонким клиентом;
- бэкенд агрегирует запросы, кеширует данные, отдаёт готовые DTO;
- переключение через `VITE_API_MODE=backend` (заготовка уже есть в `config.js`).

Подробный чек-лист задач, идеи по функционалу и план миграции — в [CHECKLIST.md](./CHECKLIST.md).
